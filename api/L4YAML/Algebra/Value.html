    Value Algebra for YamlValue (Algebra Items 18–21) #

    Algebraic properties of stripAnchors and adaptForFlowContext:

    • Item 18 — stripAnchors_idempotent
    • Item 19 — adaptForFlowContext_idempotent
    • Item 20 — stripAnchors ∘ adaptForFlowContext commutativity
    • Item 21 — pipeline idempotence: (strip ∘ adapt)² = strip ∘ adapt
    • §7 — strip and adapt commute with resolveAliases over a table of cleaned values (cleaned_resolveAliases_comm)

    These properties justify the addAnchor pipeline in ParseStateIx.lean and Parser/State.lean: cleaned = (val.stripAnchors.adaptForFlowContext).resolveAliases ps.anchors ensure WellFormedAnchors is preserved when re-processing anchor values, and show (§7) that cleaning the raw value first — linear in the anchor's own syntax, sharing the substituted subtrees — stores exactly the value the resolve-first order (val.resolveAliases A).stripAnchors.adaptForFlowContext would have, so the reorder is a pure cost change.

      theorem L4YAML.Algebra.Value.cleaned_resolveAliases_comm (v : YamlValue) (A : Array (String × YamlValue)) (hA : ∀ (p : String × YamlValue), p ∈ A → Cleaned p.snd) :
      (v.resolveAliases A).stripAnchors.adaptForFlowContext = v.stripAnchors.adaptForFlowContext.resolveAliases A

      The addAnchor reorder is exact. Over a table of cleaned values, resolving first and cleaning the (expanded) result is the same value as cleaning the raw value and resolving afterwards. The right-hand side is what addAnchor stores: it walks only the anchor's own syntax and shares every substituted subtree, where the left-hand side rebuilds the whole expansion.

      Chain (Rule 1): the specification of addAnchor's order in both parser states; the capstones that read the anchor table (parse_sound_*, parse_complete, universal_roundtrip's alias path) hold for the linear-cost order by this equation — see Blueprint/04-capstones.md, "Significance & risk".
