    [104] c-ns-alias-node — the route is inhabited #

    A definition nothing has instantiated is not yet evidence, so this file spends the alias route on the one input it exists for: &x [*x], an anchored sequence whose only item is an alias to its own anchor. YAML 1.2.2 permits it — §3.2.1.3 legislates the equality of a node that "has itself as a descendant (via an alias)" and nowhere forbids one, and §3.2.2.2 binds an alias to the most recent event carrying the anchor, which the anchored collection's start supplies.

    YamlValue expresses sharing by substitution and nothing else, so composing this shape leaves a .alias in the result. Grammable has no alias constructor, so the chain ends in Scannable and reaches ValidNode through scannableValue_has_witness. The last lemma below is the conclusion of the capstone parseStream_respects_grammar_unconditional, discharged for this input.

    The #guards record what the runtime does with the same shape today: compose maps the anchored and unanchored trees to the same value, and the style-aware writer loses the &x while keeping the *x. Both are properties of compose, not of the proofs above, and they are what plan row 5a(v)'s load-side edit addresses.

            The PARSE-side table for the same shape (plan row 20 / step 5a(vi)) #

            The route above is the COMPOSE side. The parser carries a second table — ParseState.anchors, written by addAnchor at node finalization — and WellFormedAnchors asks that every value in it be Grammable after stripping. For this input that is false, and the two lemmas below say why in the two ways it can be said: Grammable has no alias constructor at all, and the AllAliasesResolve premise that the Grammable-valued composition (compose_value_grammable) takes is false at the state the parser is actually in when it finalizes &x over [*x] — the collection's anchor binds only after its items are resolved, so its own interior alias never sees it. The parse-side leaf that used to take that premise is gone: ParserWfaProofs and IndexedWfa now ask only that an anchor value be Scannable.

            ParserWfaScannable mirrors that table onto Scannable, and the third lemma spends the mirror on this input: finalizing &x over [*x] keeps the table WellFormedAnchorsS. These three are the consumer probe plan row 20 names — they are what says the remaining parse-side clique is a rename and not a redesign.

            §6.9.2's tolerated duplicate: the start event carries the LAST & #

            scanFiltered refuses two consecutive & outright (invalidNodeProperties '&'), but validateNodeProps tolerates a duplicate when the content is a collection start — the scanner's retroactive insertion makes that case real (suite 6BFJ) — and the capstones quantify over token ARRAYS, not over scanner output. There the two anchors are distinguishable: the node's start event carries only &b, so *a names no node and is refused, while *b is bound by the same node's finalization.

            That is why parseNodeProperties declares from the COMPUTED properties rather than from each & it reads: a superseded name left in the declaration set would be aliasable and never bound, and capstones 3.6/3.7 — the resolution reading — would be false over their own domain.

            Anchor scope is per document, on ALL FOUR pipelines #

            parseStreamLoop exists four times — the load and raw paths, and the event path's own copy in Output/Events.lean and Output/EventsIx.lean — and each carries its own per-document reset. §3.2.2.2 makes anchor scope per document, so the two registers have to be cleared together: a reset that cleared the resolution table and left the DECLARATION set would let document 2 alias document 1's anchor on the event path while the load path refused it. The 2026-10-02 flip patch did exactly that to two of the four, and no test in this repo would have caught it, which is why the rows below read all four.
